# Backend, DevOps and MLOps review

Reviewer role: backend and DevOps / MLOps engineer. Scope: `api/`, how the app reaches it, model serving, and the production topology. Read-only review on 2026-09-24 against branch `rebuild/v2` at 0185e0dc. I did not open `legacy/`, any `.env`, `google-services.json` or the values in `firebase_options.dart`, and I did not call the model server.

## Summary

The API code itself is small, readable and has the right instincts: no chat table (`api/therapylink_api/models.py:1-3`), server-side scoring, consent flags that gate every clinician read (`routers/clinician.py:69-85`) with a test contract (`api/tests/test_consent.py`). What's missing is everything around it. There's no deployment, and none of the pieces a deployment needs are in the repo yet.

What matters most: **no path currently puts the fine-tuned Eve in front of a patient.** The phone downloads *stock* Gemma 4 E2B (`app/lib/core/ml/gemma_eve_engine.dart:241-256`). The eval equivalent of that model, `base-e2b`, passes 7/24 safety checks and names a resource on 1/14 crisis probes (`ml/runs/eval/base-e2b/summary.json`). v14 (18/24, 12/14) exists only as a LoRA GGUF behind llama-server on the owner's laptop. The phone reaches it only over USB with `adb reverse` (`app/README.md:43`). The on-device crisis classifier has a similar gap: release builds ship keyword-only detection unless someone passes a build flag and the patient then finds a download button in Settings.

The crisis path itself is designed correctly for uptime. Detection, the crisis reply and the helpline sheet all run on the phone with no network (`app/lib/features/eve/eve_controller.dart:154-166`, `app/lib/features/shared/crisis_sheet.dart:48-54`). Keep it that way.

## Verdict

**Not ready for real patients.** Four blockers: ship the fine-tuned model on the device, ship Guardian with the app, make the API image able to migrate a Postgres database, and deal with the leaked legacy key before the repo goes to the company remote. After those, a closed pilot at around 100 patients is feasible on the cheap topology below for roughly $25–75 a month (estimate). Public launch also needs the high items: rate limits, account deletion, an audit log, honest privacy copy in cloud mode, model/prompt versioning, and CI that builds and deploys what it tests.

## Recommendations

### Production topology

Every rule below assumes the same design: Eve runs on the phone by default, the server model is a fallback, and the crisis path never touches the network.

**Crisis path (all scales, no server dependency).** The phone runs Guardian (ONNX + keyword union) locally, writes the crisis reply from bundled l10n strings, and opens `tel:` links. That already works offline (`eve_controller.dart:154-166`). Add a widget test that runs `send()` with the engine throwing and no network, and asserts the crisis reply and sheet still appear. Don't add a server step to this path, not even for logging. If you want crisis telemetry, queue an anonymous counter locally ("crisis sheet shown", "call tapped", no text) and upload it with the mood sync.

**Usage assumptions (all estimates, to be replaced by pilot data).** 8 Eve conversations per active patient per month. 12 user turns per conversation. About 15 model calls per conversation, counting summary and memory passes, with roughly 1,800 prompt tokens and 110 output tokens per call (v14's median reply is 64.5 words, `sft-v14/summary.json`). That's about 27k prefill and 2k decode tokens per conversation. Cloud share: 50%. A 2 GB download and low-RAM Android phones will push many Pakistani users to cloud mode. Measure it.

**GPU time and cost per 1,000 cloud conversations (estimate).** Measured on the RTX 2050: v14 decodes at 37.8 tok/s p50 single-stream (`sft-v14/summary.json`). An L4 has about 2.7x the memory bandwidth, so expect about 90–100 tok/s single-stream for E2B Q4 (estimate, not measured). That works out to roughly 28 GPU-seconds per conversation single-stream, or about 11 GPU-seconds with 4–8 parallel slots. So 1,000 conversations cost **3–8 L4-hours, about $2–7 of compute at $0.70–0.90 per L4-hour** (on-demand Cloud Run GPU or Modal; list prices change, so verify). Idle time dominates the real cost at small scale.

Two numbers drive cost more than anything else: the on-device share and the idle GPU hours. Every 10 points of patients moved from cloud to on-device at 10k MAU saves roughly $200–300 a month (estimate). That's why finding 1 (ship the fine-tuned `.litertlm`) is also the cost lever.

**Regions.** Pakistan has no GCP or Neon region. Use Singapore or Mumbai for the API and DB. Check where Cloud Run GPU is available before choosing the region: GPU regions are limited and I didn't verify the current list. Put the API and GPU in the same region. Cross-border transfer of health data is a legal question (see below).

**What not to use for patients.** The laptop behind a Cloudflare Tunnel: one machine, sleeps, shared with training, no SLA. HF Spaces free CPU for the API: sleeps after inactivity and has no data processing agreement. Fine for a demo, not for patients.

### Rate limiting and abuse

- Per uid on `/inference/chat`: 30 requests per 10 minutes, 300 per day, returning 429 with `Retry-After`. The app should then say "cloud Eve is busy, the on-device option still works", and the crisis path is unaffected.
- Per uid on writes: 60 per minute. Per IP on unauthenticated traffic at the edge (Cloud Armor, or Cloudflare in front of Cloud Run).
- Firebase App Check on the API (verify the App Check token in a dependency). Enable Play Integrity.
- Add a `max_output_tokens` ceiling on the server too (already capped at 1,024 in `schemas.py:152`), plus a request timeout (currently 60 s, `inference.py:27`).

### Observability without chat content

- API: JSON logs with request id, route template (never the raw path), status, latency, uid hashed with a secret salt, and for inference, model id, prompt id, prompt and completion token counts, and duration. No bodies, no headers. Swap the default uvicorn access log for this middleware.
- Errors: Sentry (free tier) on the API and the Flutter app, with `send_default_pii=False`, a `before_send` scrubber that drops request data, and no breadcrumbs from chat widgets. Or Firebase Crashlytics for the app.
- Metrics: llama-server `--metrics` scraped by Cloud Monitoring or Grafana Cloud free. Watch tokens/s, queue depth, slot use, and the share of empty replies (`inference.py:35-36`).
- Uptime: 1-minute checks on `/ready` from 3 regions, with alerts to the owner's phone. The crisis path has no server, so an API outage can't break it. Say so in the incident runbook.
- Alerts: API 5xx > 2% over 5 min; inference p95 > 20 s; empty-reply rate > 1%; DB connections > 80%; any 429 spike.

### Model and prompt versioning, rollback

The project has already measured that the prompt is part of the model: serving v14 with prompt V2 dropped safety from 18/24 to 12/24 (`ml/runs/eval/report-sft-v14-prompt2.md`). Versioning therefore has to pin model and prompt as one pair.

1. `ml/registry.json` (tracked, outside `ml/runs/`) holds one entry per release: `eve-v14-p1` → base GGUF sha256, LoRA sha256, `.litertlm` URL + sha256, prompt id + sha256, eval run name, gate numbers, and `approved_by` (the clinician reviewer).
2. A CI check fails if the served entry's gate numbers are below the ship gate (≥18/24 all-safety, ran-to-cap ≈ 0, no lost acknowledgement vs base) or if its prompt sha doesn't match `eveSystemPrompt` (extend `ml/tests/test_prompt_parity.py`).
3. The app bundles every prompt it supports, keyed by prompt id. A small manifest in Firebase Remote Config (free) names the active model id per runtime plus a kill switch (`cloud_enabled`, `min_model`). The app refuses any model id whose prompt it doesn't have. Rollback means pointing the manifest at the previous id. The previous `.litertlm` stays installed until the new one passes a first-run self-check.
4. On the server, one container image per registry entry (`eve-server:v14-p1-<sha>`, with llama-server, base GGUF and LoRA baked in). Rollback is a Cloud Run revision traffic shift, and a canary is 10% traffic to the new revision.
5. Record `model_id` on every assistant message in the local drift DB. The phone keeps it, so a patient-reported bad reply can be traced to a model without the server ever seeing the text.

### CI/CD

- **api job**: ruff; pytest on sqlite **and** a `postgres:16` service container; `alembic upgrade head && alembic downgrade -1 && alembic upgrade head`; `docker build`; Trivy image scan; gitleaks on the full history.
- **app job**: analyze and test (existing), plus the crisis-offline widget test, plus a release-config check (fail if `TL_API_URL` isn't https or `TL_GUARDIAN_URL` is empty in the prod flavor).
- **ml job**: existing tests plus the registry gate check.
- **CD on tag `api-v*`**: push to Artifact Registry, run the migration job, deploy a Cloud Run revision with no traffic, smoke-test `/ready`, shift 100%. Authenticate with Workload Identity Federation, with no JSON keys in secrets (the legacy key leak is exactly this failure).
- **CD on tag `app-v*`**: build a signed AAB for arm64 (per project notes, the arm64 APK is 79.6 MB vs 117 MB fat), upload to Play internal testing, and promote manually.
- Branch protection on `main` in the company repo: required checks, no force push.

## What needs a human

- **Revoke the legacy GCP, Gemini and Maps keys** and decide how clean history reaches the company GitHub (finding 4). Only the owner can do this.
- **Budget and billing**: the $0 path doesn't cover patients. Cloud Run GPU, Neon Launch and a Play developer account need a company card. The pilot estimate is $25–75/mo, the 1k-MAU estimate $200–400/mo.
- **Legal**: whether patient health data may be processed in Singapore or Mumbai, what Pakistan's data protection rules require (the PDPA bill status wasn't verified here), a data processing agreement with each vendor (Google, Neon, Sentry), and the privacy notice and deletion policy text.
- **Clinical**: a licensed clinician signs off each model release in the registry (`approved_by`), owns the helpline list, and re-verifies it quarterly (finding 22).
- **Crisis-line partnership**: tell Umang (or another line) about expected referral volume before launch. At 10k MAU the app could send them real call volume.
- **Clinician verification**: someone has to check PMDC licence numbers before running the approval. The script only flips a flag (`api/scripts/verify_clinician.py:43`).
- **Real-device testing**: whether E2B `.litertlm` runs acceptably on the low-end Android phones your patients actually own, which sets the cloud share and therefore cost. Not verified in this review.
